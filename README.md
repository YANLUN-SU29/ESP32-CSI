## 1. 這個專案在做什麼

從 ESP32 擷取 Wi-Fi 的底層通道資訊 (CSI, Channel State Information)，經訊號處理後判斷
**畫面外的人有沒有在呼吸、呼吸率是多少**。

適用情境：睡眠監測、長照看護——這類場合裝攝影機有隱私問題，戴感測器又不舒服。

**目前狀態**：呼吸偵測已完成驗證（留一交叉驗證正確率 85.0%，呼吸率推估 12.4~13.1 次/分）。
心跳與大動作偵測尚未校準。AI 建模尚未開始。

## 2. 原理：為什麼 Wi-Fi 能偵測呼吸

**CSI 是什麼**
Wi-Fi 用 OFDM 把一個通道切成很多條「子載波」，每條子載波各自有自己的通道響應。
CSI 就是這些響應的量測值，是**複數**——包含振幅（訊號衰減多少）與相位（延遲多少）。

**為什麼呼吸會影響它**
無線訊號從路由器到 ESP32 會經過多條路徑（直線、牆壁反射、人體反射），這些路徑疊加後
形成「多徑效應」。人的胸腔起伏會改變反射路徑的長度，進而改變疊加結果——所以 CSI 會隨
呼吸產生**週期性的微小變化**，頻率就是呼吸頻率（約 0.2 Hz，也就是 12 次/分）。

**為什麼這件事很難**
胸腔起伏造成的調變大約只有振幅的 **1%**，而 CSI 本身的變異主要來自：
- 寬頻雜訊
- AGC（自動增益控制）漂移
- 環境中其他物體的擾動

所以「把訊號濾到呼吸頻段然後看波形」是**行不通的**——帶通濾波後的波形永遠長得像正弦波，
**連空房間的資料也是**。這是本專案最重要的一個教訓，詳見
[第 8 節](#8-判定方法與校準)與[第 11 節](#11-開發過程中的重要發現)。

## 3. 系統架構與資料流

```
┌──────────────┐   Wi-Fi 封包    ┌──────────────┐
│  路由器 (Tx) │ ◄────────────── │  ESP32 (Rx)  │
│  MERCUSYS    │ ──────────────► │  NodeMCU-32S │
│  N300        │   回傳單播封包   │              │
└──────────────┘                 └──────┬───────┘
                                        │ USB 序列埠
                    ESP32 每收到一個封包就       │ 921600 baud
                    產生一次 CSI 事件            │ CSI_V3 文字行
                                        ▼
                              ┌────────────────────┐
                              │    monitor.py      │  即時錄製
                              │  ・解 I/Q → 振幅/相位 │
                              │  ・擷取 110 條子載波   │
                              │  ・即時視覺化 + 存 CSV │
                              └─────────┬──────────┘
                                        │ data/*.csv
                          ┌─────────────┴─────────────┐
                          ▼                           ▼
              ┌────────────────────┐    ┌────────────────────┐
              │  analyzer_gui.py   │    │  batch_analyze.py  │
              │  單檔互動式分析      │    │  整批分析 + 門檻校準  │
              └────────────────────┘    └────────────────────┘
```

**關鍵設計:ESP32 為什麼要主動戳路由器**

ESP32 的 CSI 引擎只在收到**單播**封包時才會觸發，廣播封包（如信標）會被過濾掉。
所以韌體必須主動製造往返流量：每 10ms 向路由器 Port 80 送一個極小的 TCP 封包，
逼路由器回傳 ACK，才能持續產生 CSI 事件。這就是程式碼裡說的「TCP 敲門」。

**分析流程（`analyzer_gui.py` / `batch_analyze.py` 共用）**

```
110 條子載波振幅
   │
   ├─ 逐條清理：Rolling MAD 去離群值 → 線性去趨勢
   │
   ├─ 逐條帶通濾波到目標頻段（呼吸 = 0.15~0.4 Hz）
   │      ⚠️ 順序關鍵：必須「先濾波再融合」，不可顛倒（見第 11 節）
   │
   ├─ PCA 融合成 PC1 波形 ──────────────► 給人看的波形圖
   │
   └─ 逐條算 Welch PSD ────────────────► 判定用的客觀指標
            ├─ 峰值突出度
            └─ 載波共識度
```

## 5. 快速開始

### 步驟 1：燒錄韌體

1. Arduino IDE 開啟 `firmware.ino`
2. 修改 `ssid` 與 `password` 為你的路由器設定
3. 開發板選 ESP32 Dev Module，燒錄
4. **燒完務必關掉 Arduino IDE 的序列埠監控視窗**——序列埠一次只能被一個程式開啟

### 步驟 2：安裝 Python 套件

```bash
pip install -r requirements.txt
```

### 步驟 3：錄製資料

```bash
python monitor.py EMPTY01
```

會開啟一個即時視覺化視窗並同時寫入 `data/CSI_EMPTY01_<時間>.csv`。
關閉視窗即結束錄製。

啟動時應該看到：

```
[自動] 鎖定唯一 USB 裝置：COM3 (Silicon Labs CP210x USB to UART Bridge)
[連線] 已開啟 COM3 @ 921600 baud
[韌體] CSI_V3 格式 | 原始長度 256 bytes (128 條子載波) | RSSI -41 dBm | HT (11n)
[擷取] LLTF 54 條 + HT-LTF 56 條 = 110 條
[記錄] 振幅 + 相位，CSV 共 221 欄
```

結束時會輸出品質報告，**這兩個數字要是 0**：

```
- 訊號斷點：0 次
【丟失率分析】總丟失率：0 筆 (0.00%)   ✓ 無任何丟失
```

不是 0 的話那筆資料品質有疑慮，建議重錄。

### 步驟 4：分析

```bash
# 單檔互動式檢視
python analyzer_gui.py

# 整批分析 + 門檻校準
python batch_analyze.py
```

## 6. 三支程式詳解

### `firmware.ino` — ESP32 韌體

| 設定 | 預設值 | 說明 |
|------|-------|------|
| `USE_ICMP_PING` | `0` | 觸發方式。0 = TCP 敲門（已驗證）；1 = ICMP ping（程式碼備用，未實測） |
| `CSI_QUEUE_LEN` | `24` | CSI 事件佇列長度（約 9.4KB） |
| `stbc_htltf2_en` | `false` | 關閉冗餘的 STBC 區塊，讓每行由 384 降到 256 bytes |

**架構重點**：CSI 回呼**只**把資料丟進 FreeRTOS 佇列就返回，絕不在回呼裡做序列埠輸出。
原因見[第 11 節](#11-開發過程中的重要發現)。輸出由 `loop()` 負責排空。

**輸出格式**：
```
CSI_V3,<序號>,<長度>,<RSSI>,<型別>,<累計丟棄>,<I1>,<Q1>,<I2>,<Q2>,...
```

### `monitor.py` — 即時錄製

| 設定 | 預設值 | 說明 |
|------|-------|------|
| `RECORD_PHASE` | `True` | 是否一併記錄相位（CSV 由 111 欄變 221 欄） |
| `GAP_WARN_THRESHOLD` | `0.5` | 超過幾秒沒收到資料就警告 |
| `WINDOW_SIZE` | `100` | 即時視覺化的滑動視窗幀數 |
| `SUBCARRIER_IDX` | — | 子載波擷取索引，依實測佈局寫定（見[第 7 節](#7-csv-資料格式)） |

**用法**：
```bash
python monitor.py            # 互動模式，程式會問標籤
python monitor.py EMPTY01    # 直接指定標籤
```

> ⚠️ 程式內的 `VALID_LABELS = ["Empty_Room", "Walking", "Waving"]` 是早期遺留的預設選項，
> 與現行資料集命名（`EMPTY01`、`GEO_P0`、`HOLD_P10`）不符。直接用命令列指定標籤即可。

### `analyzer_gui.py` — 單檔互動分析

四種分析模式，用 RadioButton 切換：

| 模式 | 頻段 | 用途 | 已校準 |
|------|------|------|--------|
| 大動作 | 0.05 ~ 5.0 Hz | 走動、起立坐下 | ✗ |
| **呼吸** | **0.15 ~ 0.4 Hz** | **靜止人員呼吸** | **✓** |
| 心跳 | 0.8 ~ 2.0 Hz | 心跳偵測嘗試 | ✗ |
| 空房間基準 | 0.05 ~ 5.0 Hz | 確認無人時底噪 | ✗ |

> 突出度的數值尺度會隨頻段寬度系統性改變，所以門檻只在有 ground truth 的頻段成立。
> 未校準的頻段 GUI 會顯示灰色「尚無實測校準」，數值僅供不同檔案間相互比較。

**三層圖表**：
1. **全景子載波疊加** — 觀察多徑衰落，並標出該頻段最強的一條
2. **目標頻段融合波形** — 先帶通、再 PCA 融合的結果
3. **功率頻譜 (Welch PSD)** — 縱軸正規化為突出度倍率，可直接對照門檻線

> ⚠️ **判讀請以第 3 張圖為準。** 第 2 張的波形無論有沒有人都像正弦波，
> 空房間資料同樣會呈現規律起伏——這正是需要客觀指標的原因。

### `batch_analyze.py` — 批次分析與校準

```bash
python batch_analyze.py                # 分析振幅（預設）
python batch_analyze.py --phase        # 一併分析相位
python batch_analyze.py --band heart   # 改分析心跳頻段
python batch_analyze.py --no-cache     # 忽略快取重算
```

輸出內容：逐檔指標 → 分組彙總 → 各指標 AUC → 現行門檻驗證 →
**留一交叉驗證（誠實估計）** → 零誤報門檻掃描。

分組規則依檔名前綴：`CSI_EMPTY*` → 對照組、`CSI_GEO_<位置>*` → 呼吸、
`CSI_HOLD_<位置>*` → 閉氣對照。

## 7. CSV 資料格式

現行格式共 **221 欄**：

| 欄位 | 說明 |
|------|------|
| `Timestamp` | 錄製時間戳（`HH:MM:SS.ffffff`，微秒精度） |
| `L1_A`~`L63_A`、`H65_A`~`H127_A` | 110 條子載波的**振幅** |
| `L1_P`~`L63_P`、`H65_P`~`H127_P` | 對應的**原始相位**（弧度，未做 CFO/SFO 校正） |

欄名規則：`L` = LLTF 區塊、`H` = HT-LTF 區塊，數字是原始振幅陣列的索引，
`_A` = 振幅、`_P` = 相位。

**子載波是怎麼挑的**

韌體輸出 256 bytes = 128 條子載波，分成兩個 64 條的區塊。實測量出的佈局：

| 區塊 | 索引範圍 | DC 離群值 | 保護頻帶 | 取用 |
|------|---------|----------|---------|------|
| LLTF | 0 ~ 63 | idx 0（振幅 134.4，區塊中位數僅 17.6） | 28 ~ 36 | `1~27` + `37~63`（54 條） |
| HT-LTF | 64 ~ 127 | idx 64 | 93 ~ 99 | `65~92` + `100~127`（56 條） |

`analyzer_gui.py` 會依 `_A` / `_P` 後綴**只取振幅欄**做分析——相位的物理意義與尺度都
與振幅不同，混進同一個 PCA 會破壞融合結果。

**向下相容**：三種歷史格式都能讀（已回歸測試）

| 格式 | 總欄數 | 分析取用 | 有效載波 |
|------|-------|---------|---------|
| 最舊 `Sub_0`~`Sub_51` | 53 | 52 欄 | 43（動態剔除 9 條全零） |
| 中間版 `L1`~`H127`（無後綴） | 111 | 110 欄 | 110 |
| 現行含相位 `_A`/`_P` | 221 | 僅 110 個 `_A` 欄 | 110 |

## 8. 判定方法與校準

### 為什麼不能看波形

帶通濾波後的波形永遠像正弦波，**空房間也一樣**。這是濾波器的必然結果，不是訊號。
早期曾以「Welch PSD 在 0.15~0.4 Hz 抓到峰值」作為偵測成功的依據，但後來加入對照組
才發現**空房間同樣會在該頻段長出峰值**，那個結論是空的。

### 兩個客觀指標

| 指標 | 定義 | 意義 |
|------|------|------|
| **峰值突出度** | 最強子載波的帶內峰值 ÷ 帶內雜訊中位數 | 訊號比雜訊突出幾倍 |
| **載波共識度** | 前 10 強子載波中，峰值頻率彼此一致的比例 | 多條子載波是否**獨立地**收斂到同一頻率 |

共識度是**必要條件**，不是加分項。實測空房間曾出現突出度 5.5 但共識度僅 80% 的假峰值
——單看突出度做不到零誤報，必須靠共識度剔除。

### 現行門檻

```
突出度 ≥ 5.5  且  載波共識度 ≥ 90%   →   判定為偵測到呼吸
```

> ⚠️ **突出度的數值尺度會隨 `WELCH_WINDOW_SEC` 改變。**
> 若調整 Welch 窗長，門檻必須連同重新校準。兩者定義在 `analyzer_gui.py` 開頭，
> 並在註解中互相標註。

**Welch 窗長為什麼是 30 秒**

窗越短→分段越多→平均越充分→假峰值越少，代價是頻率解析度變差。實測掃描：

| 窗長 | 頻率解析度 | AUC | 對照組最高分 |
|------|-----------|-----|------------|
| 60s | 0.017 Hz | 0.917 | **24.0**（約 1~2 段平均，幾乎沒平均到） |
| **30s** | **0.033 Hz** | **0.958** | **5.5**（約 4 段平均） |
| 20s | 0.050 Hz | 0.958 | 3.1（解析度不足，命中率反而掉） |

實測對照組的「錄製時長 vs 突出度」相關係數為 **r = −0.818**——錄越短、假峰值越高，
證實假峰值來自 Welch 平均不足。

### 重新校準流程

錄了新資料之後：

```bash
python batch_analyze.py
```

看輸出的「零誤報門檻掃描」與「留一交叉驗證」，決定新門檻後改
`analyzer_gui.py` 的 `TH_HIGH_PROM` / `TH_HIGH_CONS`。

## 9. 目前成果

基於 2026-09-08 錄製的 20 筆資料（空房間 5、呼吸 12、閉氣 3），110 條含相位格式。

### 分組結果

| 組別 | n | 突出度 | 共識度 | 推估呼吸率 |
|------|---|-------|-------|-----------|
| EMPTY（無人） | 5 | 3.3 | 54% | 17.1 ± 3.2 次/分 |
| HOLD（閉氣） | 3 | 3.4 | 83% | 10.9 ± 1.3 次/分 |
| GEO_P0 | 3 | 20.4 | 97% | 12.5 ± 0.1 次/分 |
| GEO_P05 | 3 | 7.7 | 80% | 13.1 ± 0.5 次/分 |
| GEO_P10 | 3 | 15.9 | 100% | 12.4 ± 0.2 次/分 |
| GEO_P15 | 3 | 15.5 | 100% | 12.4 ± 0.2 次/分 |

呼吸組的推估頻率集中在 12.4~13.1 次/分、組內標準差僅 ±0.1~0.5，落在生理合理範圍且
高度可重複；對照組則隨機散佈（±1.3~3.2）。

### 判別力

| 指標 | 數值 |
|------|------|
| AUC | **0.958** |
| **留一交叉驗證正確率** | **85.0%**（敏感度 91.7%、特異度 75.0%） |
| 同批評估正確率 | 95.0%（命中 11/12、誤報 0/8） |

> ⚠️ **對外請引用 85.0%。** 那個 95% 是「用同一批資料選門檻，再拿同一批評估」，
> 屬於在訓練集上評估，有 10 個百分點的樂觀偏誤。
> 特異度偏低（75%）的原因是對照組只有 8 筆、每一筆都是撐住門檻的臨界樣本
> ——需要擴充對照組資料。

## 10. 常見問題與陷阱

### 找不到 COM Port / `OSError(22, '參數錯誤')`

ESP32 沒被 Windows 認到。`monitor.py` 只會挑有 VID/PID 的 USB 裝置，所以不會誤鎖主機板
內建的 COM1，但仍需檢查：

1. **USB 線** — 很多充電線只有供電、沒有資料線，這是最常見的原因
2. **驅動** — NodeMCU-32S 多為 CP2102 或 CH340，要裝對應驅動
3. **裝置管理員** — 看「連接埠」或「其他裝置」有無帶驚嘆號的項目
4. 換一個 USB 孔（前面板孔有時供電不足）

### 序列埠被佔用

`monitor.py`、`batch_analyze.py`（不需序列埠）、Arduino IDE 的序列埠監控視窗
**不能同時開著**。錄製前先確認只有一個程式在用。

### 錄完發現丟失率不是 0

看終端機的丟失率分析：
- **「韌體自報丟棄」> 0** → 序列埠排不及，可加大 `CSI_QUEUE_LEN`
- **「序號跳號」> 0** → 傳輸中遺失
- **「行截斷損壞」> 0** → 序列埠壅塞導致行被切斷

### 開機時出現一筆解析錯誤

正常。ESP32 重開機時會吐出一段二進位開機訊息，`monitor.py` 會把它記為 1 筆解析錯誤。
該筆**不會**被算進丟失率（那是刻意分開計數的）。

### 帶通後的波形看起來有呼吸，但判定是低信心

**相信判定，不要相信波形。** 帶通濾波器的輸出永遠像正弦波。請看第 3 張 PSD 圖，
確認峰值有沒有超過門檻線。

### 錄製時長建議

至少 **2 分鐘**。Welch 窗長是 30 秒，錄 100 秒約有 4 段平均，錄 120 秒有 7 段——
段數越多，對照組的假峰值越被壓下去。

## 11. 開發過程中的重要發現

這一節記錄「為什麼程式碼長這樣」。**修改前請先讀過對應項目**，這些都是踩過坑才得到的。

### PCA 融合的順序不能顛倒

常見做法是「PCA 融合 → 帶通濾波」。實測顯示這樣**完全分不出有人呼吸與空房間**
（呼吸組 3.48 vs 空房間 3.60，Cohen's d = −0.07）。

原因：PCA 以最大化變異量為目標，而原始振幅的變異由寬頻雜訊與 AGC 漂移主導，
遠大於胸腔起伏的約 1% 調變——PC1 鎖到的是**雜訊主軸**，不是生理訊號。

改成「逐條帶通 → 再 PCA 融合」後才明顯分離（65.90 vs 3.45）。

### 判定要用最強單一子載波，不是融合訊號

融合訊號適合畫波形給人看，但拿來判定的判別力差很多（AUC 0.74 vs 1.00）。
現行判定走「最強單一子載波突出度」+「載波共識度」。

### 子載波擷取範圍曾經是錯的

舊版寫死 `amplitudes[5:57]`，結果：
- 存了 9 條**恆為零**的保護頻帶（52 欄裡有 17% 是垃圾）
- 視窗兩端切在**滿振幅**上（漏掉 LLTF 的 11 條有效子載波）

實測量出佈局後改為依區塊選取，可用子載波由 43 條增至 110 條（+156%）。
另發現 STBC-HT-LTF2 區塊與 HT-LTF 的逐條相關係數達 **0.902**（冗餘），予以捨棄；
而 HT-LTF 與 LLTF 相關性僅 **0.06**，是獨立的通道量測，值得納入
——實測單用 HT-LTF 的 AUC (0.948) 甚至高於單用 LLTF (0.917)。

### fps 的瓶頸在序列埠，不在 MAC 層

曾依「每 78ms 週期有 47ms 閒置」推論 fps 卡在 59 是路由器 TCP delayed ACK 所致，
**此判斷有誤**。

證據：把每行長度縮到 2/3（384→256 bytes）後，樣本間隔中位數**精確地**由 8.00ms
降到 5.00ms、fps 升到 85。這個等比關係說明叢發內的間隔就是序列埠傳一行的時間
——序列埠排不及時，ESP32 端的 CSI 事件就被丟棄。

### CSI 回呼裡不能做序列埠輸出

回呼跑在 Wi-Fi driver task 的 context。一行約 490 bytes 在 921600 baud 下需約 5ms 的
阻塞寫入，會卡住該任務，使驅動**不再送入後續 CSI 事件**——而這種「事件根本沒進到回呼」
的損失，在 PC 端連計數器都測不到。

所以回呼只做 `memcpy` 進佇列（非阻塞），由 `loop()` 排空。佇列滿就明確計數，
損失才從不可見變成可量測的數字。

### PC 端時間戳受 USB 幀率量化

樣本間隔全都落在整數毫秒上（8.000 / 47.000 ms），這是 USB 1ms 幀率的特徵。
也就是說 PC 端量到的間隔反映的是 **USB 交付節奏**，不是 CSI 真正被擷取的時刻。
要解析真實取樣時序，需要在韌體端加入 `esp_timer_get_time()`（尚未實作）。

### 相位目前不可用

已錄下原始相位，但以 unwrap + 逐封包跨子載波線性去趨勢處理後，AUC 僅 **0.375**
（低於 0.5，即反向）。所有組別（含空房間）的推估頻率都收斂到 9.1~9.9 次/分、
共識度多為 100%，全部擠在頻段下緣 0.15 Hz 附近——這是**殘留低頻漂移洩漏**的特徵，
不是呼吸訊號。

不代表相位本身沒價值（文獻上相位常比振幅靈敏），但現行校正方法顯然不足。
可嘗試的方向：更強的高通、或改用子載波間的相位差（conjugate multiplication）。

## 12. 已知限制

### 資料量不足（目前最大瓶頸）

對照組僅 8 筆，留一交叉驗證顯示**每一筆都是撐住門檻的承重牆**——拿掉任何一筆，
門檻就會被選歪。特異度只有 75%。

建議補到：EMPTY 10+、HOLD 8+、每個位置的呼吸 5+。

### `GEO_P05` 系統性偏弱

突出度 7.7，其他位置都 15~20，且 `R2` 完全失敗（3.2 / 共識 40%）。但只有 3 次重複，
分不清是位置本身的幾何問題還是單筆意外。需要更多重複才能判斷。

### 僅呼吸頻段完成校準

心跳（0.8~2.0 Hz）與大動作（0.05~5.0 Hz）頻段缺乏對照組資料，GUI 已標示為未校準。

> 曾在住家測試中於心跳頻段看到突出度 90.8、推估 69.1 次/分（落在合理靜息心率範圍），
> 但該頻段零校準，且環境漂移的能量會漏進 0.8~2.0 Hz，**不可視為偵測到心跳**。

### 韌體未過濾來源 MAC

任何裝置的封包都會觸發 CSI，鄰居的 Wi-Fi 流量也會混入資料。

### 其他

- 進階分析與 AI 建模（CWT、EMD/VMD、CNN/LSTM 分類、Transfer Learning）尚未開始
- 無自動化測試
- 輸出為 ASCII 十進位，每個 int8 用 2~5 字元傳送（約 3~4 倍膨脹）；
  改二進位預估可將 fps 推至 120~160
